# VRCX-Cloud 单账号 Web 服务端 — 详细规划与设计（v3，私有化部署版）

## 0. 总体架构

**VRCX-Cloud = 单进程 axum 服务器，内嵌一个完整的 VRCX-0 headless 运行时（单账号、自建 VRChat 会话：实时 WS + API 直连），运行时通过已实现的 SQLite↔PG 双向同步（RemoteSyncHost 直连 PG），与用户桌面端 VRCX-0 在同一个 PG 数据库中收敛——服务端就是同步网格里的"第二台设备"，这正是该协议的本职设计场景（单账号多设备）。** React 前端原样复用，Tauri IPC 换 HTTP/WS shim。

```
用户局域网（自托管，如家庭服务器/NAS）：
┌─ 浏览器 React SPA ── POST /api/invoke + WS /api/events + GET /api/img ──┐
│                                                                        ▼
│                                              crates/server (axum, 单账号)
│                                                └ RuntimeHostState（Server profile）
│                                                   ├ RealtimeHostRuntime（VRChat WS + API 直连）
│                                                   └ RemoteSyncHost（直连 PG，已实现）
│                                                        ▼
│                                              PostgreSQL（局域网，docker-compose 提供）
│                                                        ▲
└─ 桌面端 VRCX-0（现有 SettingsSyncTab 填同一 DSN）──────┘
```

不做：多租户、邀请码、同步中继、schema-per-user、持久层 PG 重写。全部沿用已跑通的同步特性。

## 1. 核心设计决策

| 决策        | 选择                                                                           |
| ----------- | ------------------------------------------------------------------------------ |
| 部署形态    | 单账号、局域网私有化自托管优先（docker-compose / 单二进制）                    |
| 数据平面    | 服务端自有 SQLite + RemoteSyncHost 直连 PG（零改动复用）；桌面端用现有直连同步 |
| VRChat 会话 | 服务端自建（WS + API 直连）；与桌面端构成同账号双设备，经同步协议收敛          |
| Web 认证    | 单密码：首次访问设置向导（默认开启，可显式关闭），会话 cookie                  |
| 前端        | 复用 VRCX-0 前端 + `src/platform/web/` 传输层 shim                             |

## 2. Phase 0 — 代码基线（约 0.5 周）

1. 将 VRCX-0 工作区**未提交的同步代码**（~6,900 行：`application-sync`、`contracts/src/sync.rs`、`outbound-adapters/src/remote_sync_postgres.rs`、`persistence/src/sync.rs`、`composition/src/state/remote_sync.rs` 等）应用为 VRCX-Cloud 提交（两仓库 HEAD 树一致，patch 干净）；建议 VRCX-0 侧同步 commit 防 drift。
2. 删除桌面产物：`crates/host-desktop`（16.4k）、`crates/vr-overlay`（1.6k）、`crates/overlay-runtime`（6k）；`src-tauri/` 命令包装搬迁后删（P2）；`runtime-host-desktop` 拆出服务端安全模块（`local_data/social/vrchat_remote/group/avatar/media/world_remote/external_api/assistant_adapters/database_upgrade`）后删桌面半区。约 -38k LOC。

## 3. 服务端运行时（Phase 1，约 1~2 周）

### 3.1 `RuntimeHostProfile::Server`（application-core，小改）

- 新 profile 变体：secrets 加密写入允许（等价 Desktop，密钥继续用现有 `machine_uid` 派生——单机单账号下成立）；`RuntimeHostStateBuilder::finish()` 允许其挂 profile extension（现仅拒绝 HeadlessData）。
- 新 crate `crates/runtime-host-server`：`ServerRuntimeHostState` facade = `composition::RuntimeHostState` + 上述服务端安全模块；不含游戏日志 watcher/托盘/通知 sink/VR overlay/更新器。

### 3.2 `crates/server` 单运行时引导

- 配置（TOML/env）：`data_dir`、`listen_addr`、`pg.*`（同步 DSN 字段）、`web.auth.*`（密码哈希存储于 data_dir 下服务端私有 JSON，不进 SQLite configs、不同步）。
- 启动：构造 `RuntimeHostState`（Server profile）→ 首次启动把 `remoteSync.enabled/host/port/user/password/database` 写入其 SQLite configs（RemoteSyncHost 自动开始同步）→ `start_backend_runtime`（非交互 auth：cookie 有效则自动登录，过期置 `NeedsLogin`）→ axum serve。
- VRChat 登录/2FA：复用现有命令驱动的登录流（桌面登录本就由前端命令驱动，Web 上直接复用组件）。
- 进程内单运行时，无注册表/生命周期管理器；优雅停机。telemetry 服务端默认关。

## 4. Web 传输层与命令层（Phase 2，约 2~3 周）

### 4.1 `crates/server/src/transport/`

- `auth.rs`：首次访问设置向导（设密码，argon2id）→ 登录 → cookie session + CSRF；`web.auth.disabled=true` 可显式关闭（纯内网信任环境）。
- `invoke.rs`：`POST /api/invoke {cmd,args}` → `HashMap<&str, HandlerFn>` 分发；未注册命令返回结构化 `unsupported_on_web`（前端 HostCapabilities 已有降级机制）。
- `events.rs`：`WebRuntimeEventSink` 实现 `RuntimeEventSink`（emit → broadcast → WS `{event,payload}`，与 Tauri 事件同形，覆盖现有 47 个事件名）；断线重连走已有快照命令（`appBackendRuntimeCombinedSnapshotGet` 等）水合。
- `img.rs`：`GET /api/img/{kind}/{hash}` 读 `ImageCache/`，替代 `vrcx-0-img/thumb/bg-img` 自定义协议；CORS 下载代理（`appExternalApiImageDataUrlGet`）原样保留。
- `static_files.rs`：托管前端 dist。

### 4.2 命令层搬迁（机械）

- `src-tauri/src/commands/{local,vrchat,application,integrations}`（~6.4k LOC 薄包装）迁入 `crates/server/src/commands/`：`State<'_,AppState>` → `Arc<ServerRuntimeHostState>`、去 `#[tauri::command]` 保 `#[specta::specta]`。约 360 个命令可用；`commands/host/*`（~150 个窗口/托盘/剪贴板/对话框/更新器）不搬。
- integration-api / MCP 内嵌服务 v1 关闭（端口进程级、与多实例/无头场景冲突；后续如需挂 Web 认证）。

### 4.3 TS client codegen

- `crates/server/src/bin/export-web-bindings.rs` 仿 `src-tauri/src/bindings_export.rs`：specta 导出类型 + 生成 fetch 版 `commands` 对象 → `src/platform/web/bindings.ts`。前端 409 个 import 零改动。

## 5. 前端改造（Phase 3，约 2~3 周）

- 新增 `src/platform/web/`：`invoke.ts`（fetch + cookie）、`events.ts`（WS + 指数退避重连）、`assets.ts`（自定义协议 URL → /api/img 路由映射）、`webview.ts`（21 个窗口函数 web 空实现）。
- 2 个 `@tauri-apps/plugin-fs` 直接依赖（`navigationCacheStore.ts`、`quickSearchHistory.ts`）→ localStorage。
- `VITE_PLATFORM=web` 构建开关；桌面 UI（窗口装饰/托盘/侧栏吸附/更新器/截图库/游戏启动）经 HostCapabilities 屏蔽：web 能力集 `gameLogWatcher:false, gameLaunch:false, screenshotCache:false, steamLibraryDiscovery:false, websocketRuntime:true`。
- 新页面：首启设置向导 + 登录页、"同步状态"面板（复用 `SyncStatusSnapshot`，显示桌面端设备在线/同步延迟）。VRChat 登录/2FA 复用现有组件。

## 6. VRCX-0 桌面端配合改动

必须：无（直连同步已跑通，桌面继续用现有 SettingsSyncTab 填同一 PG DSN）。
建议小改：

1. `SYNC_EXCLUDED_CONFIG_KEYS` 扩充 `remoteSync.host/port/user/database/intervalSec` 等实例级键（现仅排除 password），避免桌面↔服务端 configs LWW 互覆同步设置本身。
2. 双实时会话双写去重：桌面与服务端都产 feed 行（键含各自 `created_at`，同一事件可能双行）。v1 在 feed 查询侧同窗去重 + 每用户开关 `server.realtime.feedLogging`（桌面为主时可关服务端 feed 记录，保留在线状态与 API 能力）。

## 7. 部署（Phase 5，约 0.5~1 周）

- `docker-compose.yml`：`app`（多阶段构建：cargo-chef + node build 前端 + distcp 进镜像）+ `postgres:17`（数据卷）；`.env` 配 DSN/密码/端口。
- 也提供裸机单二进制 + 系统 PG 的路径（config TOML）。
- 文档：局域网部署指引；**明确不建议公网暴露**（Web 层持有 VRChat 会话与全部社交数据），远程访问建议 Tailscale/WireGuard；PG 允许 `allow_plaintext` 仅限可信内网（现有开关）。
- NTP 对时要求（HLC/LWW 正确性）。

## 8. 阶段与里程碑（单人合计约 7~11 周）

| 阶段 | 内容                                                                    | 估时     |
| ---- | ----------------------------------------------------------------------- | -------- |
| P0   | 同步代码并入、删桌面 crate、基线提交                                    | 0.5 周   |
| P1   | Server profile + runtime-host-server 拆分 + 单运行时引导 + 同步自动配置 | 1~2 周   |
| P2   | axum 传输层（auth/invoke/events/img）+ 命令搬迁 + TS codegen            | 2~3 周   |
| P3   | 前端 platform/web + 设置向导/登录/同步面板 + 能力门控                   | 2~3 周   |
| P4   | VRChat 登录/2FA Web 流打磨 + 双写去重/开关                              | 1~2 周   |
| P5   | docker-compose、部署文档                                                | 0.5~1 周 |

里程碑：**M1**（P2 末）浏览器端到端可用：登录 Web → 服务端 VRChat 会话 → feed/游戏日志（桌面同步而来）渲染 → 双端修改互达；**M2**（P3 末）日常可用版；**M3**（P5 末）可分发私有化部署包。

## 9. 风险与已知问题

1. **双实时会话双写**（桌面 + 服务端）→ feed 重复行：P4 查询侧同窗去重 + `feedLogging` 开关。
2. **VRChat 风控**：自托管服务器 IP 首登可能触发 captcha（无自动处理，UI 透传错误；WebClient 已支持 SOCKS5/CONNECT 代理可作出站旋钮）；同账号两个自动化客户端的 ToS 风险自担（原桌面 + 服务器均在用户自己控制下，风险可控）。
3. **多实例全局态**：`group_calendar.rs:106-107` 两个 `OnceLock` 进程级缓存——单账号场景无跨租户问题，仅做记录（如未来多账号需改 per-state）。
4. **fork 漂移**：VRCX-0 上游演进（尤其同步目录/协议版本）需定期回灌 VRCX-Cloud；`sync.protocolVersion` 有前向保护。
5. **activity 页聚合**：`_activity_*` 派生缓存不同步，服务端从同步来的 feed/gamelog 源行本地重算（`_activity_sync_state_v2` 增量复放，M1 验证；不成立则参照 persistence/activity 全量构建路径）。
6. **首启引导顺序**：服务端先空 bootstrap 或桌面先上传均收敛（协议 merge/push 相位已验证）；文档引导"先配桌面或先登 Web 皆可"。
7. `configs` LWW 桌面↔服务端互覆：多数是"设置同步"特性；实例级键（remoteSync.*）按 §6-1 排除加固。

## 10. 验收标准（M1）

- 单进程部署于用户内网：浏览器登录 → 服务端自动恢复 VRChat 会话（或走 Web 2FA 登录）→ 好友实时推送 <3s（服务端 WS 自产）；桌面游戏日志 ≤60s 出现在 Web；Web 修改备忘 ≤60s 到桌面（经 PG 同步）；`_sync_devices` 可见两台设备互达。
- 前端全部核心页面可用：好友 feed/历史、游戏日志、备忘/笔记、收藏、通知、统计；桌面专属功能（截图库/游戏启动/VR overlay 等）在 Web 上被能力门控优雅隐藏。
- 杀进程重启：运行时自动恢复、同步自动续传、浏览器断线重连水合。
